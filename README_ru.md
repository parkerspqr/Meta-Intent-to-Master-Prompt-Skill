# Meta Intent Orchestrator

**Meta Intent Orchestrator** — это meta-skill для Codex, который нужен для одного главного эффекта:

> **превращать слабые, размытые, сложные, многослойные или недоформулированные пользовательские запросы в гораздо более сильное исполнение, чем даёт обычный прямой prompt.**

Он делает это не за счёт простого “улучшения формулировки”, не за счёт выбора роли из готового списка и не за счёт банального route-to-execution.

Вместо этого skill скрыто строит **правильную внутреннюю интеллектуальную рамку под конкретную задачу**, а уже потом решает саму задачу.

---

## Зачем вообще нужен этот проект

Обычная проблема большинства AI-ответов не в том, что модель “плохо пишет”.

Проблема глубже:

- пользователь часто формулирует задачу неполно;
- важнейшие требования оказываются скрытыми в подтексте;
- конфликт между “что сохранить” и “что радикально улучшить” явно не описан;
- задача может требовать не просто экспертизы, а **предельной сущности мышления**, которую пользователь сам не умеет правильно задать;
- обычный direct prompt слишком быстро переходит к исполнению;
- в результате модель выдаёт:
  - шаблонный ответ,
  - поверхностную интерпретацию,
  - красивую, но не ту структуру,
  - или generic-решение, которое формально выглядит “хорошо”, но по сути проигрывает.

Этот проект создавался именно ради того, чтобы **разорвать этот паттерн**.

### Главная ценность проекта

Самая большая ценность Meta Intent Orchestrator в том, что он не просто “помогает писать prompt-ы”.

Он делает гораздо более сильную вещь:

> **Он строит скрытую систему, которая сначала рождает правильную глубину мышления под задачу, и только после этого позволяет модели начать работать.**

Проще говоря:

- не пользователь должен вручную придумывать идеальную роль;
- не пользователь должен вручную писать сверхсильный system prompt;
- не пользователь должен вручную строить flow prompt;
- **skill делает это внутри себя сам**, а пользователь получает уже результат более высокого класса.

Именно в этом заключается главный выигрыш:

- **больше глубины**
- **больше точности**
- **меньше банальности**
- **меньше generic AI-output**
- **больше совпадения с реальным намерением пользователя**
- **выше потолок качества результата**

---

## Какую проблему решает этот skill

Этот skill нужен для задач, где прямой prompt почти всегда недостаточен.

Например:

- сложный редизайн сайта;
- переосмысление визуальной системы бренда;
- задачи, где нужно одновременно **сохранить сущность** и **радикально поднять класс формы**;
- стратегические творческие задачи;
- архитектурные задачи;
- задачи, где пользователь сам чувствует, что “обычный GPT-ответ будет слишком простым”;
- задачи, где нужна не просто информация, а **правильная интеллектуальная рамка исполнения**.

Классический пример:

> “Сделай редизайн главного экрана сайта в luxury-tech эстетике уровня Apple, но без потери текущей концепции бренда. Сохрани сетку контейнера и hero-структуру, но полностью переосмысли визуальную иерархию, стили заголовков, композицию текста и ощущение премиальности. Не делай типовой GPT-дизайн и не скатывайся в клише.”

Такой запрос:
- достаточно сложный,
- содержит скрытые противоречия,
- требует вкуса, дисциплины, архитектурности,
- требует сохранить важное и одновременно сильно улучшить,
- и почти всегда проигрывает, если модель идёт в исполнение слишком рано.

Именно для таких случаев и создавался этот проект.

---

## Центральная идея

Meta Intent Orchestrator — это **не обычный intent-to-execution skill**.

Это **hidden meta-orchestrator**.

Он работает не так:

`запрос пользователя -> уточнение -> ответ`

А так:

`запрос пользователя -> определение глубины задачи -> скрытое построение task-specific предельной сущности -> скрытое построение task-specific system+flow prompt -> выполнение через эту рамку -> результат`

Именно это делает проект особенным.

---

## Что проект делает на самом деле

Внутри skill есть два режима.

### 1. Лёгкий режим
Для простых локальных задач.

Например:
- перекрасить текст;
- подвинуть элемент;
- изменить один параметр;
- ответить на узкий технический вопрос.

В таком случае полная meta-цепочка не нужна, и skill не должен переусложнять работу.

### 2. Глубокий режим
Для сложных, многослойных, творческих, стратегических и архитектурных задач.

И вот здесь включается настоящая логика проекта:

1. skill получает сырой пользовательский запрос;
2. определяет, что задача требует не прямого исполнения, а meta-обработки;
3. скрыто порождает **предельную task-specific сущность**;
4. затем скрыто порождает **внутренний system prompt + flow prompt**;
5. использует эту внутреннюю операционную систему;
6. и уже через неё решает задачу пользователя.

---

## Два ключевых примитива

В центре проекта лежат **два пользовательских примитива**, которые были найдены и выделены не как абстрактная теория, а как реально рабочая ручная механика.

Это крайне важно.

Проект строился не вокруг выдуманной логики “сформируй роль, потом сформируй prompt”.

Он строился вокруг **двух конкретных формообразующих сообщений**, из которых вручную рождался сильный итоговый master prompt.

### Primitive 1
Первый примитив нужен для рождения **предельной профессиональной сущности** под конкретную задачу.

Его смысл не в том, чтобы просто назвать роль.

Его смысл в том, чтобы:
- подняться от обычной профессии к предельной сущности;
- найти не просто релевантную экспертизу, а **максимальный интеллектуальный режим**, нужный под задачу;
- породить не label, а **богатое ролевое ядро**.

### Primitive 2
Второй примитив нужен для того, чтобы:
- взять уже полученную предельную сущность;
- отрефлексировать её;
- и превратить не в красивое описание, а в **операционную систему мышления**:
  - system prompt,
  - flow prompt,
  - дисциплину,
  - ограничения,
  - стандарты,
  - и маршрут работы.

---

## Почему примитивы здесь критичны

В этом проекте примитивы — не декоративная часть и не иллюстрации.

Они — **ядро механики**.

Их нельзя:
- свободно переписывать;
- сокращать до сухих инженерных функций;
- заменять обычными “generate role / generate prompt” шагами;
- терять их ритм, эскалацию и скрытую динамику.

Они должны:
- **адаптироваться под задачу пользователя**,
- но при этом сохранять структуру,
- давление,
- движение к предельной сущности,
- и рефлексивный переход к system+flow prompt.

---

## В чём был самый сложный нюанс проекта

Один из главных архитектурных рисков выяснился уже в процессе.

Сначала казалось, что достаточно сделать так:

- Primitive 1 -> короткая роль
- Primitive 2 -> master prompt

Но это оказалось ошибкой.

### Почему
Если Primitive 1 выдаёт слишком короткий результат:
- название роли,
- пару абзацев,
- и краткое summary,

то Primitive 2 начинает рефлексировать **на слишком бедный материал**.

А в реальной ручной механике Primitive 1 должен рождать **не summary, а полноценный role dossier**:
- смежные направления,
- поля власти,
- несколько названий,
- выбор лучшего названия,
- глубокое описание сущности,
- различие с соседними ролями,
- ролевое ядро для агента,
- краткую предельную формулу.

И только после этого Primitive 2 даёт действительно сильный system+flow слой.

### Что это значит practically
Одной из ключевых сложностей проекта стало не просто “сохранить примитивы”, а правильно зафиксировать:

> **Primitive 1 должен выдавать не короткую сущность, а богатый многослойный материал, достаточный для второй рефлексивной стадии.**

Это один из важнейших инсайтов проекта.

---

## Почему проект не равен “prompt improver”

Очень важно не перепутать этот skill с обычным улучшателем prompt-ов.

Он не делает просто это:

- “переформулирует запрос красивее”
- “раскладывает задачу по bullets”
- “выбирает роль из списка”
- “добавляет пару ограничений”

Он делает более глубокую вещь:

> **создаёт скрытую интеллектуальную архитектуру под задачу, а уже потом решает её.**

Разница огромная.

Потому что в обычном prompt improvement:
- пользователь всё равно остаётся главным источником framing quality.

А здесь:
- framing quality строится внутри самой системы.

---

## Что делает результат лучше обычного

Если всё работает правильно, то этот skill поднимает задачу на другой уровень за счёт следующих эффектов:

### 1. Более точное понимание намерения
Skill не реагирует только на поверхность текста.

### 2. Более правильная глубина мышления
Skill не использует “один режим на всё”, а порождает нужную глубину под задачу.

### 3. Меньше банальных ответов
Обычный generic-output становится менее вероятным.

### 4. Меньше преждевременного исполнения
Skill не спешит отвечать там, где сначала нужно построить правильную рамку.

### 5. Больше архитектурности
Особенно в сложных творческих и стратегических задачах.

### 6. Больше fidelity к настоящей задаче пользователя
То есть ближе не к буквальному тексту, а к реальному запросу по сути.

## Архитектура проекта

В текущем виде проект состоит из:

- `SKILL.md` — основной control plane;
- `agents/openai.yaml` — metadata-интерфейс skill-а;
- `references/protocol.md` — скрытый внутренний протокол;
- `references/primitive-matrices.md` — описание и защита двух примитивов;
- `references/session-policy.md` — удержание task-frame и логика новой задачи;
- `references/examples.md` — ключевые режимы поведения на живых кейсах.

### Что важно в этой архитектуре
Логика специально разнесена так, чтобы:
- не перегружать один файл;
- не терять control plane;
- сохранить явную структуру продукта;
- отделить протокол, матрицы, session behavior и examples.

## Как проект создавался

Проект не родился как готовая концепция с самого начала.

Он собирался итеративно через несколько слоёв осмысления:

### Этап 1. Выявление ручной механики
Сначала был замечен сам паттерн:
пользователь вручную пишет первый сильный запрос на предельную роль,
потом второй — на анализ этой роли и сборку system+flow prompt,
и только потом через получившуюся рамку работает дальше.

### Этап 2. Понимание, что это не просто prompt-chain
Потом стало ясно, что это уже не просто хорошая переписка с моделью, а **повторяемая скрытая механика**, которую можно превратить в skill.

### Этап 3. Ошибка схлопывания
Потом появилась ошибка:
была попытка слишком рано упростить продукт до “intent -> role -> answer”.
Это оказалось неверно.

### Этап 4. Возврат к настоящей сути
После этого продукт был переопределён как:
- hidden meta-orchestrator,
- а не обычный intent-execution layer.

### Этап 5. Защита примитивов
Затем стало понятно, что главная опасность — потерять сами примитивы, превратив их в абстрактные функции.
Это было исправлено.

### Этап 6. Выявление проблемы с выходом Primitive 1
Потом выяснилось, что мало защитить вход примитива.
Нужно ещё жёстко защищать **богатый формат его выхода**.

### Этап 7. Поведенческие тесты
После этого skill был проверен на:
- простой локальной задаче;
- сложной задаче с блокирующей неясностью;
- новой независимой задаче;
- и положительном deep-path сценарии.

И только после этого стало понятно, что продукт по сути уже работает правильно.

---

## Какие были основные сложности

### 1. Не схлопнуть продукт в обычный skill
Это была самая большая опасность.

### 2. Не потерять примитивы
То есть не заменить их сухими инженерными функциями.

### 3. Не переусложнить простые задачи
Потому что если skill будет всегда запускать полный meta-loop, он станет неудобным.

### 4. Наоборот, не упростить сложные задачи
Это противоположная опасность.

### 5. Удержать внутреннюю рамку внутри одной задачи
И при этом не тащить её в новый task.

### 6. Скрыть внутреннюю кухню
Пользователь не должен видеть весь hidden chain по умолчанию.

### 7. Не превратить deep mode в красивый разговор вместо реального исполнения
Это тоже проявилось в живых тестах: логика была сильной, но внешний runtime сначала показывал слишком много процесса и недожал deliverable до конца.

## На каком этапе проект сейчас

На данный момент:

- core-логика skill-а уже собрана;
- hidden two-stage chain реализован;
- различение простых и сложных задач реализовано;
- session frame policy реализована;
- task boundary реализован;
- поведенческие smoke-тесты пройдены;
- positive deep-path подтверждён;
- архив собран;
- формальная локальная валидация пройдена.

### Но важно
Проект нельзя считать “абсолютно завершённым навсегда”.

На текущем этапе корректнее говорить так:

> **Skill уже готов как рабочий продукт, но ему всё ещё требуется больше времени на тестирование, наблюдение за реальным поведением и тонкую настройку runtime-слоя.**

Это особенно касается:
- внешнего UX,
- степени скрытия внутренней кухни,
- жёсткости момента, где Primitive 1 должен углубляться,
- и полировки того, как skill доводит сложную задачу до полного deliverable без лишних промежуточных остановок.

## Что уже можно считать успешным

Уже сейчас можно считать, что проект достиг своей главной цели:

- он не распался на обычный generic orchestration;
- он действительно удержал идею скрытого meta-уровня;
- он способен не просто решать задачу, а **сначала порождать правильную внутреннюю интеллектуальную систему под неё**.

А это и было самым ценным.

## Что дальше

Следующий естественный этап развития проекта:

### 1. Расширенное runtime-тестирование
Нужны ещё реальные задачи из разных доменов:
- дизайн,
- бренд,
- продукт,
- коммуникация,
- архитектурные решения,
- сложные conceptual tasks.

### 2. Полировка output behavior
Особенно:
- меньше служебной телеметрии наружу,
- меньше раскрытия process trace,
- сильнее доведение до deliverable в том же ответе.

### 3. Усиление quality gate для Primitive 1
То есть ещё жёстче закрепить:
- нельзя переходить к Primitive 2, если результат Primitive 1 слишком бедный.

### 4. Debug-mode
Очень полезным следующим развитием может стать debug-режим:
- для автора,
- для тестов,
- для анализа того, какой maximal entity и какой internal prompt pair реально порождаются.
